# Sapphros Threat-Informed Attack Validation

I built this Python and Ansible security validation lab to map controlled adversary
emulation with defensive telemetry, Sigma detections, repeatable validation, and
documented security findings.

The recorded exercise ran on September 19, 2026. Its findings describe that run;
they do not assert current host health or continuous detection coverage.

This project is being developed as a practical demonstration of detection
engineering, cybersecurity automation, adversary emulation, and technical
documentation.

Detection Engineering · Incident Response Analysis · MITRE ATT&CK · Sigma ·
Sysmon · Python · Ansible · Windows Security · Security Automation

### Detection-Engineering Finding

During T1003.001 validation, Defender prevented the simulated
`rundll32.exe` / `comsvcs.dll` LSASS dump before the attacker process
generated the expected Sysmon telemetry. Sysmon ProcessAccess events in the
same window were instead generated by Defender's own `MsMpEng.exe` process.

A source-process-blind LSASS rule could therefore have misclassified Defender
remediation activity as attacker activity. The Sigma rule was tuned to exclude
Defender's own process, and the exercise was recorded as **PREVENTED** rather
than incorrectly scored as **DETECTED**.

## What I Learned

- **A telemetry match needs context.** Defender's own LSASS access resembled
  attacker activity until I checked the source process and Defender record.
- **Prevention and detection require separate outcomes.** A blocked credential
  dump does not prove that the Sigma rule detected attacker LSASS access.
- **Rule tuning has tradeoffs.** Excluding paths under `\\Windows Defender\\`
  addresses the observed false positive, but does not establish that every
  excluded process is trustworthy or that the rule is production-ready.
- **Emulation tools leave their own traces.** Sandcat-to-PowerShell thread
  creation was incidental telemetry, not an additional validated technique.
- **Automation claims should match the implementation.** The Python tool
  validates host baselines; attack-to-detection correlation remains manual.

## Baseline Validation Pipeline

The host-baseline workflow is automated:

Ansible collects host facts into JSON reports. The Python validator checks those
reports and returns PASS or FAIL. CI separately tests the Python code and committed
sample reports; it does not connect to the physical lab.

## Detection Validation Workflow

The current detection-engineering workflow is implemented and evidence-driven:

Caldera executes a controlled scenario on the Windows target. I review Sysmon
and Defender telemetry, correlate it with the operation timeline, evaluate the
Sigma rule logic, and document the resulting DETECTED or PREVENTED outcome.

## Running the Baseline Validation

From the repository root, create and activate the Python environment and install
the project (Python 3.12 or later):

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -e ".[dev]"
```

The live collection step also requires Ansible, reachable lab hosts, and an
inventory and SSH key configured for your own environment. The committed
`ansible.cfg` identifies the lab's inventory and key path.

Collect current host evidence:

```bash
ansible-playbook ansible/playbooks/health_check.yml
```

Run the Python validator:

```bash
sapphros-validate
```

Run the automated tests:

```bash
pytest -v
```
